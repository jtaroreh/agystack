### Shipping

**You own what lands. Verify each PR independently, land only the verified run from the root, then keep your hands off the stack.** For "land the stack", "ship it", "enable merge when ready", or the second half of a stack that **Babysit** already drove to green.

This is the half after `playbooks/babysit.md`. Babysit makes a stack mergeable. Shipping decides what is actually safe to merge and lands only verified PRs from the root up. Green is not safe, and the gap between those two words is where this playbook lives.

1. **Resolve the forge, then verify every PR independently before arming anything.** GitHub CLI (`gh`) is the default. If `command -v origin` succeeds and Origin can resolve the repository, use `origin pr` for every PR operation. Otherwise stay on `gh` and record the fallback. Never require Graphite (`gt`). Dispatch one `poteto-agent` subagent (`invoke_subagent`) per PR, not batched, each exercising the real surface (`browser_subagent`, CLI runner, or project verify skill) against parent versus head. Each returns `PASS`, `PASS+NOTES`, or `FAIL` and posts that verdict on its own PR so the record outlives the chat. Only a verdict from an agent that did not write the code counts. CI green and an approving bot review are not verdicts. Standardize GitHub status checks on unpiped `gh pr view <number> --json reviewDecision,statusCheckRollup -q .reviewDecision`, or use `origin pr view <pr> --checks`.
2. **Land only the contiguous verified run rooted at the bottom.** Walk up from the lowest unmerged PR and stop at the first one without `PASS` or `PASS+NOTES`. The PRs below it are the run, and the top one is the ceiling. A verified PR sitting above an unverified one waits, because merging it would pull the gap in underneath it. A verified PR whose branch neither holds nor needs the unverified code below it can be rebased onto trunk to land on its own, after taking a fresh verdict against trunk. Report the ceiling as a PR number and say what breaks the chain.
3. **Re-check that the verdicts still describe the code.** A verdict covers a patch, and a restack moves every PR above it to a new SHA without failing any check. Compare `git patch-id` at the verdict SHA with the current head before trusting an older verdict. When the patches differ only in tests, docs, or lint config, a lane's result stands if what it ran builds the same at both SHAs apart from noise. Noise is a difference that also shows up between two builds of the verdict SHA, or an embedded commit SHA. Report each kind of noise with its files so a reader can check the call. The change itself still gets fresh checks and a review because the old verdict never saw it. A lane with no build output, such as a dev server, cannot show this, so rerun it and re-verify anything else that drifted.
4. **Land bottom-up, one PR at a time.** Always merge the run's lowest unmerged PR first, using `gh pr merge <pr> --squash` (or `--merge` or `--rebase`) or `origin pr merge <pr>`. On Origin the plain command also merges every PR below the named one. On GitHub, a PR whose base is still its parent's branch merges into that branch rather than trunk, so retarget first or merge from trunk outward.

   Read the PR back for the result (`gh pr view <pr> --json state,mergedAt,baseRefName` or `origin pr view <pr>`), because a merge command can report success when a merge queue only queued the PR, and a requested auto-merge is not a merge. A landed PR reads merged with trunk as its base, not its parent's branch.

   **Auto-merge safety on stacked branches.** Arm `--auto` (`gh pr merge <pr> --auto --squash` or Origin merge-when-ready) only on a PR targeting protected trunk whose verdict covers its current head. Never enable GitHub native auto-merge on intermediate child PRs targeting unmerged parent branches, because they read `CLEAN` and merge immediately into the parent branch, collapsing review granularity.

   After each merge lands, retarget the child PR whose base was the merged branch to trunk (`gh pr edit <pr> --base <trunk>` or `origin pr edit <pr> --base <trunk>`), rebase its patch onto the merge result, and push with `--force-with-lease`. Step 3's `git patch-id` rule decides whether the verdict survives. Merge it once its checks pass and its verdict covers the head.
5. **Leave the stack alone while it lands, and watch the drain.** Step 4's move of the next PR is the only change to a branch or base, because a merge lands whatever its branch and base hold at that moment. On GitHub, watch the verified run with `$(find ~/.gemini/config/plugins/agystack .agents/plugins/agystack skills/poteto-mode -name "watch-pr" -type f 2>/dev/null | head -1) --queued-stack --stack-prs <pr1,pr2,...>` under autonomous execution (`/goal` and the `schedule` tool using `DurationSeconds` with `TimerCondition: "never"`), re-armed after any verdict you act on, until `COMPLETE` at the ceiling. `ADVANCE` is progress, not termination. Pass the exact same frozen PR list bottom-to-top on every re-arm. On Origin, re-read `origin pr view <pr> --checks` each time `origin pr checks <pr> --watch` returns until the ceiling reads merged. A base moving to trunk when its parent merges is expected, not damage. If a queue stalls, diagnose why before mutating anything.
6. **Stop at the ceiling.** When the verified run is merged, report what landed, what the next unverified PR is, and what verifying it would take. Extending the run takes new verdicts through step 1, not a judgment call made unilaterally.

**Reply:** the verified run and its ceiling, each PR's verdict and who produced it, what landed and how you confirmed it, and what the next gap needs.
