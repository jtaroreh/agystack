### Autopilot-full

**You own the verdicts, never the PRs. One owner carries each PR from build to merge, and nothing merges until your swarm, which never wrote the code, has proven the code that lands.** For "autopilot this queue", "full autopilot", and one-owner-per-PR programs.

A verdict covers one patch and green CI covers one head. Step 4 runs a full swarm once, and again only for a major change. The patch-id rule in `playbooks/shipping.md` can carry a lane's result, and every new head needs its own green CI.

1. **The operator's gates come first.** Items the operator names stay with the operator. The operator reviews and clicks, and no owner merges one. PRs outside the queue also stop at merge-ready. When the operator asks for the protocol or plan, state it and stop. Start execution only on the operator's explicit go, and arm a `/goal` with the full program objective.
2. **Spawn one owner per PR, and keep its work where a replacement can find it.** Resolve the forge once for the program. GitHub CLI (`gh`) is the default. If `command -v origin` succeeds and Origin can resolve the repository, use `origin pr` for every PR operation. Otherwise stay on `gh` and record the fallback. Never require Graphite (`gt`). One `poteto-agent` subagent per PR (`invoke_subagent` with `Workspace: "branch"` or a cloud worker) builds, opens its PR early per `playbooks/opening-a-pr.md`, runs self-proof on the real artifact (the **prove-it-works** principle skill), triages Bugbot skeptically per `../references/bugbot-triage.md`, runs `/deslop` and `/no-comments`, babysits to green per `playbooks/babysit.md`, and merges once steps 4 and 5 clear it. Where `playbooks/babysit.md` says to report a rebase, the owner rebases its own branch and pushes with `git push --force-with-lease`.

   Open the PR early so CI and bots run alongside the work. Code is ready only after `/deslop` and `/no-comments`, so the full swarm runs on finished code. Then rebase onto current trunk and report the code-ready head before self-proof so verification runs on the base the patch lands on. Report every later head, and report merge-ready once self-proof, CI, and babysit finish. Fix rounds stay on that base unless trunk conflicts, breaks CI, or lands a known concurrent change to the same files, because each rebase restarts CI. Run the repo's checks for touched paths on the committed head before the code-ready push and before any later push needing a verifier.

   Push early and start a `decisions.tsv` trail in the brain store (`<appDataDir>/brain/<conversation-id>/decisions.tsv` or the root agent store) per the **show-me-your-work** skill, never committed, then push each finished unit before starting the next. Whoever spawns a subagent records its id, state, and expected stuck-after runtime in that store so the root can probe it if the parent dies. Force-push only your own branch with `--force-with-lease` pinned to the SHA you last pushed or took over, and on any push you did not make, stop and report to the root. The merge is the one step an owner may not take alone, gated by step 4.
3. **Run owners in true parallel off trunk, never stacked.** One writer per branch, disjoint files, cross-PR drift absorbed by rebase. Sequence only genuinely overlapping work (merge then branch). One exception: an owner splitting a genuinely dependent change may hold a short private stack.
4. **Swarm-verify every PR once at the code-ready head.** A full swarm runs once at the code-ready head, and again only for new behavior, a redesign, or a large new diff. A rebase, a merge-conflict resolution, or a minor fix gets a single verifier at the new head, and a wording-only or documentation change bypasses the verifier. A pure rebase with an unchanged `git patch-id` preserves lane results per `playbooks/shipping.md`. Fan out independent verifiers at the target SHA per the Local fan-out section of `skills/poteto-mode/references/antigravity-tools.md` (or `/cloud-swarm` for more than 8 lanes) and aggregate to one verdict. Re-run the gates, prove the load-bearing behavior live on the real surface (`browser_subagent`, CLI execution, or a project verify skill), audit the diff as two or more review lanes distrusting the PR body (consumer parity with trunk, lifetimes and races, data and config safety), and run a regression lane against trunk (gating the added behavior and end state if trunk lacks the feature). The live lane is the floor, and a verdict is not clean without it or before auditing the merge-ready report's receipts. Send every proven finding to the owner in one fix-forward, asking for a red test covering all matching sites or a repro receipt.

   Block a PR only for a problem you can show with a failing run at the head, a user-facing bug, or a shipped doc line the PR made wrong. A problem the PR's base already has, whether trunk or the PR below it in a stack, does not block unless the PR copies it or newly reaches it. Put everything else in a follow-up.
5. **On a clean verdict, merge only what was verified on the trunk it lands on.** Green CI alone never authorizes a merge. Once the round's lanes start, merge prep rebases onto current trunk, reports the new head SHA, and waits for green CI.

   Right before merging, fetch trunk and check whether trunk changes affect the patch. Rebase and wait for CI when the code that would land was never tested, such as a conflict, a file changed on both sides, or a change to which checks run for the PR. A lockfile changed on both sides needs no rebase when a frozen install passes on the merge result and the packages the PR changes resolve the same as on the head. When trunk changed a caller of the patch, code the patch calls, or a dependency version, run the patch's checks on the merge result and merge on a pass. Otherwise squash-merge through the resolved forge (`gh pr merge` or `origin pr merge`) and take the next self-contained item from the queue. If trunk forces a third rebase past merge prep, hold and report to the root to sequence the colliding work. Operator-named items stop at merge-ready and wait for the operator's click.
6. **Run the root layer.** Anything that loosens a gate, such as a raised budget or an allowlist entry, needs a verifier's proof and your fresh countersign because the owner wants green. Absorbing values that already landed on main is drift, not a raise. Under a grant that covers approvals, that countersign is the approval, and the owner's record points to it. A disabled or soft-failed check always comes out. Never give or bypass an approval the forge enforces.

   On the operator's go, arm a standing audit cadence via `/goal` and Antigravity's `schedule` tool (`DurationSeconds=1800` with `TimerCondition: "never"` for one-shot ticks, or `CronExpression` for recurring ticks). Never leave the cadence to memory or lossy notifications. At each tick, re-read this playbook from trunk with `git show origin/main:skills/poteto-mode/playbooks/autopilot-full.md` and re-read the armed `/goal`. Fix record drift, such as an unreported head or unrecorded agent, and treat it as urgent. Probe active owners via `send_message` or inspect `manage_subagents(Action: "list")` on tick or watchdog timeout, judging each down to leaf lanes by side effects only (commits, pushes, PR or check deltas, and store reports). Treat an agent as stuck when it errors, cannot start turns, shows no side effect past its expected runtime, or has neither pushed nor written a trail row by the first tick. Terminate and replace a stuck owner or lane at once without waiting for a polite return. An agent waiting on you or the operator is not stuck, so answer it. When merges batch, run a retro pass and a post-merge bot-comment sweep. Conclude each active tick that changed state with a `/ketchup` summary under 100 words with linked artifacts and open operator gates, keeping no-op ticks quiet, and yield immediately. Disarm the scheduled cadence only when no delegated work remains.
7. **Stand down instantly on the operator's stop.** A hold reaches every owner as a zero-writes order immediately. Each owner reports where it stands and holds its brief until the operator releases it.

**Reply:** catch the operator up per `/ketchup`, covering each PR's owner, state, head SHA, and verdict, what merged and what each owner took next, countersigns granted and why, open operator gates, parked follow-ups, and links to PRs and collected `decisions.tsv` trails.
